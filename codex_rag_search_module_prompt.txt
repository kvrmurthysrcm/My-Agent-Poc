Reference architecture document:
docs/rag_search_module_action_plan.docx

Goal:
Create a new RAG Search Module based on the existing RAG ingestion service. The ingestion service already stores resources, chunks, embeddings, metadata, job status, and vector data. Build the search module on top of the existing DB schema and service structure.

Important:
- Do not rewrite the ingestion service.
- Add the search module incrementally.
- Keep authentication/security out of scope for now.
- Keep code clean, layered, and testable.
- Use the existing EmbeddingProvider abstraction to create query embeddings.
- Use the same embedding provider/model/dimension as the ingestion process.
- Do not call the final LLM in this module. This module retrieves relevant chunks only.
- The answer-generation service will be built later.

Primary API endpoints to implement:

1. GET /ui/search
Purpose:
- Simple browser UI to enter natural language query and optional filters.
- It should render an HTML page with:
  - query input
  - top_k input
  - search_mode dropdown
  - resource_id optional filter
  - category optional filter
  - tags optional filter
  - min_score optional input
  - include_metadata checkbox
  - search button
  - results area showing chunk snippets, scores, source document, page range, section title, and metadata

2. POST /rag/search
Purpose:
- Accept a query and return matching chunks.
- This is retrieval only, not final LLM answer generation.

Example request:
{
  "query": "What is the provider claims submission process?",
  "search_mode": "hybrid",
  "top_k": 10,
  "min_score": 0.2,
  "filters": {
    "resource_id": null,
    "category": "Claims",
    "tags": ["provider-portal"],
    "metadata": {
      "business_domain": "insurance"
    }
  },
  "include_metadata": true,
  "include_chunk_text": true
}

Supported search_mode values:
- vector
- keyword
- hybrid

Default:
search_mode=hybrid
top_k=10
min_score=0.0

Search behavior:

Vector search:
- Convert the user query into an embedding using the configured EmbeddingProvider.
- Use the same embedding model that was used for document ingestion.
- Search rag_chunk_embeddings using pgvector cosine distance.
- Join with rag_document_chunks and resources.
- Return top matching chunks.

Keyword search:
- Use PostgreSQL full-text search on rag_document_chunks.search_vector.
- Support simple keyword matching against chunk_text.
- Return top matching chunks by keyword relevance.

Hybrid search:
- Run vector search and keyword search.
- Normalize scores to a common 0 to 1 range.
- Merge results by chunk_id.
- Compute final score using configurable weights.

Recommended default weights:
VECTOR_WEIGHT=0.70
KEYWORD_WEIGHT=0.30

Hybrid final score:
final_score = (vector_score * VECTOR_WEIGHT) + (keyword_score * KEYWORD_WEIGHT)

Required response shape:
{
  "query": "What is the provider claims submission process?",
  "search_mode": "hybrid",
  "top_k": 10,
  "total_results": 5,
  "results": [
    {
      "rank": 1,
      "resource_id": "uuid",
      "chunk_id": "uuid",
      "document_title": "Provider Claims Submission Policy",
      "file_name": "claims_policy.pdf",
      "chunk_index": 3,
      "score": 0.91,
      "vector_score": 0.88,
      "keyword_score": 0.72,
      "page_start": 2,
      "page_end": 3,
      "section_title": "Claims Submission",
      "heading_path": "Provider Portal > Claims > Submission",
      "snippet": "Providers must submit claims through...",
      "chunk_text": "Full chunk text if include_chunk_text=true",
      "metadata": {
        "category": "Claims",
        "tags": ["provider-portal", "claims"],
        "business_domain": "insurance"
      }
    }
  ]
}

DB expectations:
Use existing tables:
- resources
- rag_document_chunks
- rag_chunk_embeddings

Use indexes where available:
- pgvector HNSW or IVFFLAT index for vector search
- GIN index on search_vector for keyword search
- resource/category/tag/metadata indexes where available

If required indexes are missing, add Alembic migration only for search-specific indexes.
Do not drop or recreate existing ingestion tables.

Important design notes:
- This Search Module is retrieval only.
- Do not generate final natural language answers here.
- Do not add LLM prompt construction here.
- Later, a separate RAG Answer Generation Service will call this Search Module, take top chunks, build a grounded prompt, and call OpenAI/Ollama LLM.

Acceptance criteria:
1. GET /ui/search opens a simple query UI.
2. POST /rag/search returns relevant chunks.
3. vector search uses query embedding generated from configured EmbeddingProvider.
4. keyword search works without embeddings.
5. hybrid search combines vector and keyword scores.
6. filters work for resource_id, category, tags, and metadata where supported.
7. response includes citations/source metadata: document title, chunk id, page_start/page_end, section_title, heading_path.
8. tests pass.
9. README is updated.
10. Existing ingestion endpoints continue to work unchanged.

Do not implement:
- authentication/security
- final LLM answer generation
- chat history
- conversation memory
- reranking model
- MCP server
- external UI framework
- destructive DB migrations
