# Release note — five-service SonarQube rollout

**Date:** 2026-09-16  
**Time:** 13:58:15 EDT (UTC-04:00)  
**Purpose:** Extend advisory SonarQube analysis, coverage reporting, test-result reporting, and historical metrics from Online Library to the five related Python services while leaving MCP, agents, weather services, and Angular UI for later. This clears the pipeline work before the high-priority session-aware feature.

## Included services

- RAG Ingest
- RAG Search
- RAG Answer
- Online Library
- Secure API

## Deferred services

- Online Library MCP
- Online Library Agent
- Weather Agent
- Weather AI Agent
- Angular UI

Deferred services remain present in the ten-row Sonar inventory with `NOT_CONFIGURED` status.

## Pipeline changes

Replaced the Online-Library-only execution path with a reusable service scanner. Change detection still controls which modules are built, tested, analyzed, and deployed.

Each selected pilot service now receives:

- a project-specific Sonar scan;
- a project-specific analysis token;
- Python coverage import;
- pytest execution import;
- Quality Gate wait and result;
- Git revision and Jenkins build reference;
- scanner log and concise module summary;
- metrics and history export into the shared TSV.

The five Sonar scans run sequentially in the first rollout. This adds predictable load to the local SonarQube container and simplifies troubleshooting. Existing build/test and deployment parallelism remains configurable and unchanged.

## Credential isolation

Added these Jenkins credential IDs:

- `sonarqube-token-rag-ingest`
- `sonarqube-token-rag-search`
- `sonarqube-token-rag-answer`
- `sonarqube-token` for the existing Online Library project
- `sonarqube-token-secure-api`
- `sonarqube-report-token` for shared read-only metrics/history reporting

Each project token is bound only while its service scanner runs. A missing credential affects only that service's advisory scan. Other selected services continue.

The reporting token runs in a separate export step. This prevents a reporting API problem from discarding completed scanner results.

## Coverage and test reporting

Updated the four newly onboarded Docker test stages to install `pytest-cov` and emit:

- `/tmp/test-results/pytest.xml`
- `/tmp/test-results/coverage.xml`

Added branch-aware `.coveragerc` files and targeted pytest warning configuration. Test-only dependencies remain outside runtime stages.

All five services now use the same high-level lifecycle:

1. Build the test stage.
2. Run tests and generate JUnit/Cobertura reports.
3. Copy reports into the Jenkins workspace.
4. Build the runtime image only after tests pass.
5. Run the selected Sonar scan.
6. Export current measures and analysis history.
7. Deploy the already-tested runtime image.

## Sonar configuration

Added project configurations for:

- `my-agent-poc-rag-ingest`
- `my-agent-poc-rag-search`
- `my-agent-poc-rag-answer`
- `my-agent-poc-secure-api`

The existing `my-agent-poc-online-library` configuration remains in use.

Source analysis is limited to each service's application code. Tests are identified separately, generated reports and caches are excluded, Python 3.13 is declared, and the Quality Gate result is awaited for up to 300 seconds.

## Advisory behavior

Sonar remains non-blocking. Scanner failures, Quality Gate failures, missing project credentials, and reporting failures are surfaced as advisory stage failures while deployment continues.

Application build or test failures remain blocking and prevent deployment.

## Required setup before push

Create the four new SonarQube projects and their project analysis tokens. Add all credentials to the Jenkins **System** credential store, not an individual user's store. Grant the existing reporting user Browse permission on every new private project.

The first overlay build changes shared CI files and is expected to analyze all five pilot services. Missing setup will be reported per service as `ATTENTION_REQUIRED` but will not block deployment.
