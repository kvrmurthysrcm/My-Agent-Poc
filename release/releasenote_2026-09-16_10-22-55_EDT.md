# Release Note: Sonar Build Report, Coverage, Tests, and History

**Date and time:** 2026-09-16 10:22:55 EDT (UTC-04:00)  
**Purpose:** Turn the initial Online Library Sonar proof of concept into a build-aware quality-reporting step with test coverage, test execution, a consolidated ten-module inventory, and reliable historical analysis identifiers.  
**Enforcement:** Advisory. Sonar problems and Quality Gate failures remain visible but do not block deployment. Application build or unit-test failures remain blocking.

## Outcome

The pipeline order is now:

```text
Checkout
  -> Plan
  -> Preflight
  -> Initialize Sonar Report
  -> Build and Test
  -> Sonar - Online Library (Advisory)
  -> Deploy
  -> Verify Stack
```

This sequencing is required because SonarQube imports reports generated by external test tools; it does not run pytest or calculate Python coverage by itself. Runtime images are built once during `Build and Test` and the exact tested images are reused by `Deploy`.

## Consolidated Sonar Artifact

Every service-changing build creates and archives:

```text
build-reports/sonar/sonar-summary.tsv
```

The TSV always contains one row for each of the ten pipeline services:

1. `ingest`
2. `search`
3. `answer`
4. `library`
5. `mcp`
6. `library-agent`
7. `weather`
8. `weather-ai`
9. `secure`
10. `angular`

During this incremental release, Online Library is the only Sonar-enabled module. The other rows explicitly say `NOT_CONFIGURED`; they are never represented as passing without analysis.

Important report fields include:

- Jenkins build number and Git commit
- service and Sonar project key
- selected-for-build and analyzed-this-build flags
- analysis status and Quality Gate result
- reliability, security, and maintainability ratings
- Security Hotspot count
- overall and new-code coverage
- overall and new-code duplication
- lines of code
- test count, failures, errors, skipped tests, and execution time
- latest Sonar analysis date and revision
- stable build reference
- browser-safe dashboard and history URLs
- metric source (`SONAR_API`, local XML fallback, or both)
- an operator recommendation

The initialized inventory remains available even if credentials, scanning, or metrics export fail. If the Sonar metrics API is unavailable, coverage and test totals fall back to the archived Cobertura and JUnit XML reports and identify that source in the TSV. This makes missing analysis explicit rather than silently omitting it.

## Coverage Reporting

Online Library's test image now installs `pytest-cov` and generates Cobertura XML:

```text
test-results/online-library/coverage.xml
```

The report is archived by Jenkins and copied into the scanner's isolated workspace. Sonar imports it through:

```properties
sonar.python.coverage.reportPaths=.ci-reports/coverage.xml
```

Coverage configuration is version controlled in:

```text
modules/online_library/.coveragerc
```

It enables branch coverage, records relative file paths, and excludes test code from production coverage calculations.

The coverage dependency exists only in the Docker test stage. It does not increase the Online Library runtime image.

## Test-Execution Reporting

The existing pytest JUnit XML is still published to Jenkins, using the narrowed pattern:

```text
test-results/**/pytest.xml
```

Narrowing the pattern prevents Jenkins from attempting to parse `coverage.xml` as a JUnit result.

Online Library's JUnit XML is also imported into Sonar through:

```properties
sonar.python.xunit.reportPath=.ci-reports/pytest.xml
```

This supplies project-level test count, duration, failure, error, and skipped-test measures when supported by the active Sonar Python analyzer.

## Historical Trends and Build Traceability

SonarQube continues to retain analysis history under the stable project key:

```text
my-agent-poc-online-library
```

Each analysis now sends:

- `sonar.buildString=jenkins-<build-number>-<short-commit>`
- `sonar.analysis.buildNumber=<build-number>`
- `sonar.analysis.buildUrl=<Jenkins build URL>`
- `sonar.scm.revision=<full Git commit>`

The old use of a Jenkins build number as `sonar.projectVersion` was removed. Build identity belongs in `sonar.buildString`; project version should represent a real application/release version if one is introduced later.

The TSV includes both a dashboard URL and a Sonar activity/history URL. SonarQube remains the authoritative historical store; Jenkins archives a snapshot associated with each build.

## Pipeline Separation

`scripts/ci/build-test-deploy.sh` accepts a sixth action argument:

```text
build-test
deploy
all
```

- `build-test` runs parallel builds/tests and produces the image-size report.
- `deploy` deploys the already-tested images in the existing dependency-aware waves.
- `all` preserves backward compatibility for callers that still want the previous combined behavior.

If build or test fails, Jenkins never enters the Sonar or Deploy stages. If Sonar alone fails, `catchError` keeps it advisory and deployment continues.

## Scanner Cache Improvement

The persistent volume is now mounted at the complete Sonar user-home path:

```text
/opt/sonar-scanner/.sonar
```

This keeps the scanner `_tmp` and `cache` directories on the same filesystem, removing the previous non-fatal cross-filesystem atomic-rename warnings. The new persistent volume name is:

```text
sonar-scanner-home
```

The older `sonar-scanner-cache` volume is no longer used. It can be inspected and removed manually later; this release does not delete it automatically.

## Security

- The Sonar token remains a Jenkins Secret text credential.
- The token is passed only as a masked environment variable.
- No token, administrator password, or credential value is written to the TSV.
- The analysis container remains non-root with all Linux capabilities dropped and `no-new-privileges` enabled.
- The scanner does not receive the Docker socket or Jenkins home.
- Temporary scanner workspaces and copied test reports are removed automatically.

## Expected First Build

Because this release changes the Jenkinsfile and shared CI scripts, the first build will select all services. Only Online Library receives Sonar analysis and coverage; the other nine appear as `NOT_CONFIGURED` in `sonar-summary.tsv`.

Expected Online Library evidence includes:

```text
Coverage report ... imported
Test execution report ... imported
QUALITY GATE STATUS: PASSED|FAILED
SONAR/REPORT: .../build-reports/sonar/sonar-summary.tsv
```

A Quality Gate failure may occur after coverage becomes visible. That is useful feedback and remains non-blocking during this learning phase.

## Industry-Standard Position

This release follows the normal order of producing test evidence before static analysis, importing rather than inventing coverage/test data, keeping a stable project key for trends, associating analyses with immutable Git revisions, and preserving a concise CI snapshot while SonarQube remains the detailed system of record.

The next recommended step is to inspect several Online Library builds, agree on useful coverage and new-code thresholds, and only then onboard the next Python module. Do not make the Quality Gate blocking until the imported evidence and baseline are understood.
