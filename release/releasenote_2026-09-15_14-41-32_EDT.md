# Runtime Image Size Reporting

- Date: 2026-09-15
- Time: 14:41:32 EDT (UTC-04:00)
- Purpose: make Docker runtime-image sizes visible and downloadable during every selected-service Jenkins build so image optimizations can be measured objectively.
- Scope: parallel CI/CD runtime builds, Jenkins reporting, and build artifacts

## Updates

### Per-service size measurement

Each service worker now inspects its completed runtime image with Docker immediately after the runtime target is built. The worker validates that Docker returned a numeric byte count and logs the result in both bytes and mebibytes:

```text
IMAGE/SIZE: secure-api:33-abcdef0 = 123.45 MiB (129446707 bytes)
```

The reported value comes from Docker image metadata (`docker image inspect ... --format '{{.Size}}'`). It represents the runtime image content size known to the local Docker engine. It does not include the temporary test target because test images are measured separately from, and excluded from, production runtime images.

### Parallel-safe result collection

Every parallel worker writes to its own service-specific TSV fragment under `build-reports/image-sizes/`. Workers never append to the same file, preventing interleaved or corrupted output when two services finish at nearly the same time.

The coordinator removes only the selected services' stale fragments before work begins. After all selected build/test workers succeed, it verifies that every selected service produced a valid size record.

### Consolidated size summary

Before Kubernetes deployment starts, the coordinator creates `build-reports/image-sizes.tsv` with these columns:

- `service`
- `image`
- `size_bytes`
- `size_mib`

The final row reports the combined size of all runtime images selected by that build. Jenkins console output also receives a formatted table headed `RUNTIME IMAGE SIZE SUMMARY`.

Because the summary is produced before deployment, missing or invalid image metadata fails the build before cluster changes begin.

### Jenkins artifact retention

The Jenkins `Build Test Deploy` post action now archives `build-reports/image-sizes.tsv` and fingerprints it. The report remains downloadable from the Jenkins build after the workspace is cleaned.

`allowEmptyArchive` is enabled so an earlier build failure that occurs before runtime images exist does not hide the original error with a secondary artifact-publication failure.

## First-run expectation

This release modifies shared Jenkins and CI orchestration files. The first SCM-triggered build after applying the overlay will therefore select all ten services. That produces a useful complete image-size baseline.

Subsequent module-only commits will report and deploy only the affected service or services. Markdown release notes remain documentation-only changes.

## Using the report

1. Open the Jenkins build page.
2. Download the archived `build-reports/image-sizes.tsv` artifact.
3. Compare `size_bytes` between builds for exact changes.
4. Use `size_mib` for a readable dashboard or release-note value.
5. Treat the `TOTAL` row as the combined selected-image footprint, not necessarily unique disk usage, because Docker images may share base layers.

## Validation expectations

- Every selected runtime build emits one `IMAGE/SIZE` line.
- The summary contains exactly one service row per selected service plus one `TOTAL` row.
- No deployment wave starts before the summary is successfully produced.
- Jenkins archives and fingerprints the TSV report.
- Image cleanup continues after success or failure.

## Validation performed before release

- Both modified shell scripts passed `bash -n` syntax validation.
- The compact Jenkinsfile remained approximately 5.2 KB with balanced structural braces, avoiding regression toward the earlier CPS method-size failure.
- A two-service parallel simulation generated independent Secure API and Angular size fragments.
- The simulated images were each reported as 10.00 MiB and the consolidated `TOTAL` row correctly reported 20.00 MiB.
- The size summary appeared before the first simulated Kubernetes deployment wave.
- The generated TSV contained the expected header, two selected-service records, and one total record.

## Rollback

Remove the image-inspection/report-writing block from `scripts/ci/service-worker.sh`, remove summary generation from `scripts/ci/build-test-deploy.sh`, and remove `archiveArtifacts` from the Jenkinsfile. No module Dockerfile or Kubernetes rollback is required.
