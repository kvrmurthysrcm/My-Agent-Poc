# Release Note: Advisory SonarQube Check for Online Library

**Date and time:** 2026-09-15 22:17:22 EDT (UTC-04:00)  
**Purpose:** Introduce SonarQube analysis for the `online_library` module as a visible, non-blocking quality check.  
**Scope:** Jenkins pipeline orchestration, one reusable Sonar scanner script, and version-controlled analysis properties for Online Library. Application source, Dockerfiles, Kubernetes manifests, tests, and runtime behavior are unchanged.

## Summary

The pipeline now runs SonarQube analysis after preflight and before application build/test/deployment whenever change detection selects the `library` service. The analysis waits for the SonarQube Quality Gate result and reports either `PASSED` or `ATTENTION_REQUIRED` in the Jenkins stage log and archived text report.

This first rollout is intentionally advisory:

- Application tests and image/deployment failures still fail the pipeline normally.
- A Sonar scanner, connection, authentication, background-task, or Quality Gate failure marks only the Sonar stage as unstable.
- `buildResult: 'SUCCESS'` allows subsequent stages to continue and preserves a successful overall build when Sonar is the only problem.
- Jenkins archives both a concise summary and the complete scanner log.

## Changed Files

### `Jenkinsfile`

- Adds explicit Sonar configuration values:
  - Server URL: `http://sonarqube:9000`
  - Docker network: `keycloak_keycloak-network`
  - Jenkins credential ID: `sonarqube-token`
  - Project key: `my-agent-poc-online-library`
  - Pinned scanner image: `sonarsource/sonar-scanner-cli:12.1.0.3233_8.0.1`
- Adds the `Sonar - Online Library (Advisory)` stage.
- Runs the stage only when `CI_SERVICES` contains the exact service ID `library`.
- Uses Jenkins `withCredentials` so the token is injected only for the scan and masked in logs.
- Uses `catchError(buildResult: 'SUCCESS', stageResult: 'UNSTABLE')` to make the initial rollout non-blocking.
- Archives `build-reports/sonar/**` even if analysis fails.

### `scripts/ci/sonar-online-library.sh`

- Runs the official, version-pinned SonarScanner CLI container.
- Attaches the scanner to the same Docker network as SonarQube.
- Copies the checked-out repository into an isolated, temporary Docker volume. This avoids incorrect host bind-mount paths when Jenkins itself runs in Docker and does not expose the Jenkins container's Docker socket, credentials, or unrelated mounts to the scanner.
- Removes the temporary scanner container and workspace volume after every outcome.
- Reuses analyzer downloads through the persistent `sonar-scanner-cache` Docker volume to improve later scan times.
- Drops Linux capabilities and enables `no-new-privileges` on the scanner container. It runs as root only inside the isolated container so the scanner can write its temporary work and cache paths; it receives no Docker socket or host bind mount.
- Restricts production analysis to `modules/online_library` and classifies `tests/**/*.py` as test code.
- Excludes test files and generated Python cache directories from production-source analysis.
- Identifies the project version using the Jenkins build number and short Git commit.
- Waits up to 300 seconds for the Quality Gate result.
- Produces:
  - `build-reports/sonar/online-library-summary.txt`
  - `build-reports/sonar/online-library-scanner.log`
- Never prints the Sonar token.

### `modules/online_library/sonar-project.properties`

- Keeps module-specific Sonar analysis settings beside the module source.
- Defines source and test paths without treating test files as production code.
- Excludes generated Python cache content.
- Declares Python 3.13 for language analysis.
- Enables Quality Gate polling with a 300-second timeout.
- This separation is the industry-standard direction: the Jenkinsfile orchestrates, the shell script supplies runtime integration, and module-owned analysis rules remain version controlled with the module.

## Required One-Time Jenkins Setup

1. In SonarQube, create the project with key `my-agent-poc-online-library`. Alternatively, the first-scan user must have **Create Projects** permission.
2. Create a token for a dedicated CI user. Grant only the permission required to analyze the Online Library project.
3. In Jenkins, open **Manage Jenkins > Credentials**.
4. Add a **Secret text** credential containing the Sonar token.
5. Set its credential ID to exactly `sonarqube-token`.
6. Confirm the Jenkins Credentials Binding plugin is installed; the pipeline uses `withCredentials`.
7. Push a change under `modules/online_library/**` or its Kubernetes directory to exercise the stage.

Do not store the token in Git, the Jenkinsfile, a shell script, a Docker image, or a Kubernetes manifest.

## Network Assumptions

The scanner is created by the Docker daemon and attaches to `keycloak_keycloak-network`, where the working SonarQube container is reachable as `http://sonarqube:9000`. The Jenkins container itself does not need to join that network.

If the shared network is later renamed to `platform-shared`, update `SONAR_DOCKER_NETWORK` in the Jenkinsfile only after both SonarQube and PostgreSQL/Sonar dependencies have been migrated as planned.

## Expected Jenkins Behavior

### Passing analysis

- Stage: successful
- Summary status: `PASSED`
- Pipeline: continues normally
- Recommendation: review new issues, security hotspots, duplication, and maintainability findings in SonarQube.

### Quality Gate or scanner failure

- Stage: unstable with an explanatory warning
- Summary status: `ATTENTION_REQUIRED`
- Pipeline: continues to application build/test/deployment and stack verification, and can finish successfully
- Recommendation: inspect the archived scanner log and Sonar dashboard; fix findings or connectivity/configuration before converting the gate to blocking.

### Missing Jenkins credential

- The stage is unstable/non-blocking.
- The pre-created summary remains archived with `status=NOT_RUN` and directs the operator to the stage log.
- Add the `sonarqube-token` Secret text credential and run the build again.

## Validation Performed Before Packaging

- Shell syntax check for `scripts/ci/sonar-online-library.sh`.
- Static review of exact service-selection matching.
- Static review that secrets are passed through the environment and not echoed.
- Static review that scan failure cannot change the overall Jenkins build result by itself.
- Static review that scanner reports are archived before workspace cleanup.

Live Sonar analysis is not run while producing this overlay because the Jenkins credential must be created by the administrator and the pipeline must execute inside the Jenkins/Docker environment.

## Industry-Standard Position and Next Recommendation

Industry practice is to introduce a new quality gate in observation/advisory mode, establish a clean baseline and agreed thresholds, then make the gate blocking after teams have addressed existing findings. This implementation matches the first phase.

Recommended follow-up after several successful scans:

1. Add Python coverage generation (`pytest-cov`) and provide the XML report to SonarQube.
2. Review and resolve findings on **new code** first instead of trying to clean the complete POC history immediately.
3. Configure an explicit Quality Gate appropriate for this POC.
4. Once stable, change the pipeline to fail the build on a failed Quality Gate.
5. Add Sonar checks to additional modules through the shared external script pattern, keeping the Jenkinsfile compact to avoid the earlier Groovy CPS method-size problem.

## Rollback

Remove the `Sonar - Online Library (Advisory)` stage and the five `SONAR_*` environment entries from `Jenkinsfile`, then delete `scripts/ci/sonar-online-library.sh`. No application, database, Docker image, or Kubernetes rollback is required.
