# Release note — Online Library SonarQube stabilization phase 1

**Date:** 2026-09-16  
**Time:** 12:13:27 EDT (UTC-04:00)  
**Purpose:** Increase Online Library repository-layer test coverage, separate Sonar analysis and reporting credentials, prepare a measurable new-code baseline, remove CI dependency noise, and define the controlled path for hotspot review and onboarding the next module.

## Scope and rollout decision

This release deliberately changes only the existing Online Library Sonar pilot. It does not enable SonarQube for the remaining nine modules.

That sequencing is intentional: the next module is gated on one successful Online Library build that proves the updated tests, coverage import, reporting token, history fields, deployment, and cleanup. After that validation, `rag-search-service` is the recommended second pilot because it already has 28 automated tests and uses a different project layout.

The Sonar stage remains advisory. Build and application-test failures remain blocking.

## Implemented changes

### Repository-layer tests

Added `modules/online_library/tests/test_repository.py` with isolated, database-free tests covering:

- database health response conversion;
- exposed-table inventory;
- allow-list rejection for unknown tables;
- safe table-row retrieval and parameter forwarding;
- recursive JSON conversion for UUID, date, datetime, Decimal, bytes, lists, dictionaries, and nulls;
- optional resource-column discovery;
- modern and legacy catalog SQL projections;
- all supported catalog filters and blank-input behavior;
- every supported catalog sort and the safe default;
- catalog row normalization;
- catalog search count, paging, and result conversion;
- resource detail found/not-found paths;
- catalog facets;
- generic paged search behavior;
- author, user, subscription, and approval search construction;
- unfiltered search paths.

The tests use scripted connection and cursor doubles. They do not require a live PostgreSQL database and cannot alter local or shared data.

### Coverage impact

Local verification produced:

- 32 tests passed;
- `repository.py`: 100% coverage;
- Online Library application files: approximately 87% combined line/branch coverage;
- 420 statements, 58 missed, 70 branches, and four partial branches.

The Jenkins/Linux result may differ slightly by dependency version, but the same pytest and coverage configuration is used.

### SonarQube credential separation

Added Jenkins credential ID `sonarqube-report-token` and environment variable `SONAR_REPORT_TOKEN`.

Token responsibilities are now separated:

- `sonarqube-token` is sent to the scanner container and should remain a project analysis token.
- `sonarqube-report-token` is sent to the reporting container and should be a user token owned by a dedicated read-only reporting account.

The report exporter prefers `SONAR_REPORT_TOKEN`; its previous analysis-token fallback is retained only for manual/backward-compatible execution. The Jenkins execution path supplies the reporting token explicitly.

This should resolve the history API HTTP 403 once the reporting user has Browse access to the private project. The reporting user does not need Administer Project, Administer Issues, Administer Security Hotspots, or global administrator permissions.

### New-code baseline helper

Added `scripts/sonar/configure-online-library-new-code.ps1`.

The helper configures a project-specific rolling 30-day new-code period through SonarQube's supported Web API. It requires a temporary user token in `SONAR_ADMIN_TOKEN` with Administer Project permission. It does not accept, print, or store a password and does not write a token into the repository.

The administrative token should be removed from the PowerShell environment and revoked after the setting is verified.

### Dependency and warning handling

- Replaced the deprecated TestClient `httpx` path with `httpx2` in the Docker test stage.
- Added `PIP_ROOT_USER_ACTION=ignore` to explicitly acknowledge that pip is running inside an isolated container build, eliminating the misleading root-user warning.
- Added a narrowly scoped pytest filter for Starlette 1.6.0's remaining use of AnyIO's compatibility alias. The filter names the exact upstream warning and module; it does not suppress application warnings or all deprecations.

Test-only packages remain in the Docker `test` stage and are not copied into the deployed runtime image.

### Security hotspot governance

Added `docs/SONAR_ONLINE_LIBRARY_GOVERNANCE.md` with:

- the required reviewer permission;
- evidence that must be recorded for each hotspot;
- criteria for Safe versus Fixed;
- a prohibition on bulk classification;
- pilot exit criteria;
- the proposed next-module selection.

No hotspot was automatically classified. Classification requires an authenticated reviewer to inspect the exact rule, source location, data flow, exposure, and compensating controls in the SonarQube UI.

## Required setup before pushing

Create the following Jenkins Secret text credential:

- **ID:** `sonarqube-report-token`
- **Secret:** a SonarQube **user token** from a dedicated reporting account

For a private SonarQube project, grant that account Browse permission on `my-agent-poc-online-library`. Do not use the Sonar administrator account for routine report export.

If this credential is missing, the advisory Sonar stage will be marked unstable and deployment can continue, but the scan script will not start because Jenkins cannot complete credential binding.

## One-time new-code configuration

Run from the repository root:

```powershell
$env:SONAR_ADMIN_TOKEN = '<temporary-user-token-with-administer-project>'
.\scripts\sonar\configure-online-library-new-code.ps1
Remove-Item Env:\SONAR_ADMIN_TOKEN
```

Verify the 30-day setting in **Online Library > Project Settings > New Code**, then revoke the temporary administrative token.

## Hotspot review procedure

In **Online Library > Security Hotspots**, open and review all three findings. Do not classify them based only on the aggregate count.

The review account needs Administer Security Hotspots. That permission should not be granted to the Jenkins reporting account.

## Validation performed

- 32 tests passed in an isolated Python environment.
- Repository coverage reached 100%; overall application coverage reached approximately 87%.
- The deprecated FastAPI/TestClient `httpx` warning was absent.
- The targeted upstream AnyIO compatibility warning was suppressed without hiding other warning categories.
- Python source compilation passed for the exporter and new tests.
- PowerShell parsing passed for the new-code helper.
- Docker execution could not be performed from the Codex sandbox because Windows denied access to the Docker named pipe. Jenkins remains the authoritative Linux-container verification environment.

## Expected Build 39 behavior

1. All changed shared CI/test files cause the relevant service selection logic to run.
2. Online Library executes 32 tests and generates updated `pytest.xml` and `coverage.xml`.
3. Sonar imports the expanded coverage and test results.
4. The scanner authenticates with `sonarqube-token`.
5. The TSV exporter authenticates with `sonarqube-report-token`.
6. `sonar-summary.tsv` should contain populated `analysis_date` and `analysis_revision` without `history API: HTTP Error 403`.
7. Sonar remains advisory and deployment continues regardless of its Quality Gate result.
8. Runtime image size should remain near 61.69 MiB because test dependencies are excluded from the runtime stage.
9. Kubernetes rollout and three-image retention cleanup execute as before.

## Acceptance criteria before onboarding another module

- Build and all 32 Online Library tests pass in Jenkins.
- Coverage and pytest reports are imported by Sonar.
- Report history fields are populated without HTTP 403.
- The three hotspots have documented human review decisions.
- The 30-day new-code definition is visible in SonarQube.
- Deployment succeeds and no more than three runtime CI images per service remain.

Only after these checks should `rag-search-service` be added as the next advisory Sonar project.
