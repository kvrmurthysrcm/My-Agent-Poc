## Current application logging

All three RAG services use the same application logging pattern in `app.main` and `app.trace_context`:

| Area | Current behavior |
| --- | --- |
| Log handler | `logging.StreamHandler(sys.stdout)` configured through `logging.basicConfig(..., force=True)`. |
| Console formatter | `%(asctime)s %(levelname)s %(name)s trace_id=%(trace_id)s span_id=%(span_id)s request_id=%(request_id)s %(message)s` |
| Business/request context | Service middleware stores `trace_id`, `span_id`, `parent_span_id`, and `request_id` in `ContextVar` values, and the custom `LogRecordFactory` adds them to records. |
| Request completion | The middleware emits `request_completed` with method, path, and duration fields. |
| Explicit OTel logging code | None. There is no application-created `LoggerProvider`, `OTLPLogExporter`, or OTel `LoggingHandler`. |

The three Deployments continue to set:

~~~text
OTEL_LOGS_EXPORTER=otlp
OTEL_PYTHON_LOG_CORRELATION=true
OTEL_PYTHON_DISABLED_INSTRUMENTATIONS=click
~~~

The bootstrap-installed `opentelemetry-instrumentation-logging` package is version `0.66b0`. Its installed implementation treats `OTEL_PYTHON_LOG_CORRELATION=true` as a request to inject `otelTraceID`, `otelSpanID`, `otelTraceSampled`, and `otelServiceName` into log records. Its log auto-instrumentation setting defaults to enabled, so it configures a logging handler using the SDK LoggerProvider unless explicitly disabled. The working Loki records below prove that the effective runtime has this automatic export path active.

## Distinguishing the two correlation systems

These are related but not interchangeable fields:

| Field | Source and meaning |
| --- | --- |
| `app.trace_id` / console `trace_id` | Existing application request correlation ID. It is taken from incoming W3C context when present, otherwise generated by the application middleware. |
| `app.span_id` / console `span_id` | Existing application middleware span-like ID and response-header value. It is not the OTel current span ID. |
| `request_id` | Existing application request correlation ID from `X-Request-ID` or generated by middleware. |
| `otelTraceID` | OpenTelemetry distributed trace ID. This is the field to use for Tempo-to-Loki correlation. |
| `otelSpanID` | OpenTelemetry current span ID. This is the field to use for span-level correlation. |

For requests with supplied W3C context, the app and OTel trace IDs can match because both extract the same incoming trace ID. For requests without an incoming `traceparent`, they need not match. A current no-parent Ingest health log, for example, had distinct values for `trace_id` and `otelTraceID`.

## Loki ingestion evidence

Grafana's Loki datasource returned these label names:

~~~text
deployment_environment
service_instance_id
service_name
service_namespace
~~~

The `service_name` label values prove that all three current service streams reach Loki:

~~~text
rag-answer-service
rag-ingest-service
rag-search-service
~~~

A read-only Ingest `GET /health` probe was sent with the following W3C context:

~~~text
traceparent: 00-13131313131313131313131313131313-3535353535353535-01
tracestate: acme=step13
X-Request-ID: step13-log-probe
User-Agent: Step13-Log-Probe/1.0
~~~

It returned HTTP 200. Loki found exactly one matching `request_completed` record by querying its structured `otelTraceID` field:

| Loki field | Value |
| --- | --- |
| `service_name` | `rag-ingest-service` |
| `otelTraceID` | `13131313131313131313131313131313` |
| `otelSpanID` | `6807440e9454d923` |
| `request_id` | `step13-log-probe` |
| `path` | `/health` |
| `severity_text` | `INFO` |
| `message` | `request_completed` |

Tempo retrieved the exact same trace with HTTP 200. Its FastAPI `GET /health` server span was `6807440e9454d923`, was a child of the supplied `3535353535353535` parent, and retained `tracestate=acme=step13`. That makes the Loki `otelTraceID`/`otelSpanID` pair a verified direct link to the Tempo trace/span.

The pod console line for the same request intentionally shows the different application middleware span ID:

~~~text
trace_id=13131313131313131313131313131313
span_id=60fcc54cf1c1f815
request_id=step13-log-probe
~~~

The response `traceparent` likewise used the application span ID `60fcc54cf1c1f815`, while Loki and Tempo correctly use the OTel server span ID `6807440e9454d923`. This is why dashboards and investigations should use `otelTraceID` and `otelSpanID` for distributed observability rather than assuming that the existing application `span_id` represents the OTel span.

## Decision and proposed changes

**Decision: zero-code logging is sufficient in the current lab.** Logs from all three services reach Loki with service-resource fields and validated OTel trace/span correlation. No application `LoggerProvider`, `OTLPLogExporter`, or `LoggingHandler` should be added now; doing so would duplicate the automatic SDK path and add failure modes without fixing an observed gap.

No source or runtime configuration was changed in this step.

The only remaining clarity improvement is optional and should be a separate, explicitly approved logging-format task:

1. Rename or visually distinguish the existing custom console values as `app_trace_id` and `app_span_id`.
2. Optionally print `otelTraceID` and `otelSpanID` alongside them in the console formatter, with safe defaults for non-instrumented test runs.

That presentation improvement is not required for Loki/Grafana correlation because the OTel fields are already exported as structured metadata and can be queried directly.
